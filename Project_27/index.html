Project 27: bisakah Excel produksi harian jadi KPI yang bisa diaudit? (simulasi)

Tujuan project: membersihkan dan menguji file Excel produksi harian dengan dbt + DuckDB lalu menghitung KPI (FPY, NG rate, RTY, Pareto) yang bisa diaudit. Data adalah simulasi.

Status: selesai (dashboard belum di-deploy)Manufaktur · data engineeringDATA SIMULASIdbt · DuckDB · SQL · Python
DATA SIMULASI. 150 file Excel produksi harian dibangkitkan dengan format yang berganti dan data kotor yang ditanam. Hasil menguji metode, bukan kondisi pabrik. GitHub Actions harian ditulis tetapi belum terbukti berjalan 7 hari; otomasi diuji lewat simulasi 10 run lokal.

Pertanyaan
Bisakah file Excel produksi harian yang kolomnya sering berganti dibersihkan, diuji, dan dihitung menjadi KPI yang bisa diaudit (FPY, NG rate, RTY, Pareto defect)?
Data
Simulasi: 150 file Excel (3 sheet), 9.060 baris produksi mentah, 4.199.497 unit input pada data bersih, 10 stasiun, 3 model, 2 shift, 2 Maret–25 September 2026.
Temuan utama
Burn-in Test paling buruk dengan NG rate 3,70% (stasiun berikutnya 1,35%). RTY lini 90,2%, final yield setelah rework 93,7%.
Keputusan yang didukung
Fokus perbaikan di Burn-in Test; jadikan test dbt gerbang wajib sebelum KPI dipublikasikan. Hemat sekitar 52–104 jam rekap per tahun perkiraan.
Metode
dbt + DuckDB (staging, dimensi, fakta, 60 test), SQL, chi-square, deteksi minggu turun (z robust), cek silang rekap Excel (SUMIFS, LibreOffice), benchmark 1 juta baris.
Catatan jujur
Model berpengaruh signifikan pada NG (p < 0,001) tetapi efeknya sangat kecil (Cramér V 0,010). Tidak ada lot atau serial; nama defect rekaan.

Minggu 2026-06-08: RTY 86,9%; stasiun terburuk S08 (NG rate 4,7%). Shift tidak berpengaruh (p 0,76).

Rekap langsung dari raw hanya memakai 5.400 dari 9.000 baris (kolom nama baru terlewat) dan membaca 20 stasiun, bukan 10.

VerifikasiPipeline dijalankan ulang dari nol; hasil sama dengan yang tersimpan

  • Uji dbt: 54 lulus, 6 peringatan (data kotor di raw), 0 error dari 60 test.
  • Baris kotor tertangkap uji raw: 300 dari 300 (5 jenis, cocok per file).
  • Mart sama dengan rekap Excel SUMIFS (dihitung ulang LibreOffice): 300 dari 300 lulus.
  • Bangun ulang dua kali menghasilkan tabel identik (SHA-256): 8 dari 8; dashboard tanpa error: 5 dari 5 pemeriksaan.
  • Gerbang publish terbukti menahan hasil saat skema file berubah.

Batasan

  • Data simulasi; tidak ada lot atau serial (rework hanya per hari, stasiun, model); nama defect rekaan.
  • Jam hemat adalah asumsi; benchmark bergantung mesin dan diulang 3 kali saja.
  • GitHub Actions harian ditulis tetapi belum terbukti berjalan 7 hari; otomasi hanya diuji lewat simulasi 10 run lokal.
  • Dashboard belum di-deploy; defect dalam satu stasiun terbagi hampir merata, jadi tidak ada defect dominan.
