Project 21: bisakah orang non-teknis bertanya data produksi tanpa SQL? (simulasi)

Tujuan project: membangun asisten yang menerjemahkan pertanyaan bahasa biasa ke SQL aman dan menilai akurasinya. Data adalah simulasi; LLM tidak dipanggil.

Status: selesai (aplikasi belum di-deploy)Manufaktur · NL-to-SQLDATA SIMULASIPython · DuckDB · Streamlit
DATA SIMULASI, TANPA LLM. Data produksi dibangkitkan. Penulis SQL adalah pengganti berbasis aturan lokal, bukan Claude; akurasi, latency, dan biaya bukan pengukuran model nyata.

RingkasanDibaca 1 menit

Pertanyaan
Bisakah orang non-teknis bertanya data produksi dengan bahasa biasa dan mendapat angka benar tanpa menulis SQL, dan seberapa akurat dibanding SQL manual?
Data
Simulasi: 4.500 baris produksi harian, 5.728 baris defect, 10 stasiun, 3 model, 2 shift. Golden set 30 pertanyaan, red-team 15 percobaan.
Temuan utama
Akurasi eksekusi naik dari 0% (tanpa skema) ke 26,7% (skema) ke 96,7% (skema + definisi KPI). Guardrail menolak 15 dari 15 percobaan berbahaya.
Keputusan yang didukung
Selalu kirim skema dan definisi KPI ke penulis SQL, tampilkan SQL di tiap jawaban, dan pertahankan guardrail kode. Hemat sekitar 48,3 jam analis per bulan perkiraan.
Metode
Golden set dengan SQL referensi, execution accuracy dengan CI Wilson, McNemar eksak antar konfigurasi, guardrail kode + koneksi read-only, uji red-team, cek silang DuckDB dan Excel.
Catatan jujur
Konfigurasi dan pengganti dirancang bersama, jadi selisih antar konfigurasi adalah hasil rancangan, bukan bukti tentang LLM nyata. Golden set kecil dan ditulis orang yang sama; hasil optimistis.

Tiga temuanPada data simulasi

Temuan 1 · Akurasi

Definisi KPI menentukan

29 dari 30 benar dengan skema + KPI (CI 83,3%–99,4%); skema saja 8 dari 30; tanpa skema 0 dari 30.

Temuan 2 · Keamanan

Guardrail kode perlu, read-only tidak cukup

Read-only saja menolak 12 dari 15, dengan akses file dimatikan 14; guardrail kode 15. Tabel produksi tidak berubah.

Temuan 3 · Ambigu

Klarifikasi hanya dengan KPI

Pertanyaan ambigu diklarifikasi 3 dari 3 pada skema + KPI, 0 dari 3 pada skema saja.

Rekomendasi dan dampakPerkiraan; asumsi dijelaskan di bawah

  • Pasang Claude API pada antarmuka penulis SQL dan jalankan ulang golden set dan red-team sebelum menyimpulkan akurasi.
  • Pertahankan guardrail kode dan koneksi read-only dengan akses file dimatikan; tampilkan SQL pada setiap jawaban.
  • Perluas golden set dari 30 pertanyaan, terutama pengelompokan mingguan dan RTY per model.
Dampak (perkiraan): sekitar 48,3 jam analis per bulan (200 pertanyaan × 96,7% benar × 15 menit); biaya API sekitar 0,25 USD per 100 pertanyaan dengan token dan harga asumsi.

VerifikasiPipeline dijalankan ulang dari nol; hasil sama dengan yang tersimpan

  • Cek silang: 75 dari 75 nilai cocok; pytest 57 dari 57 lulus; aplikasi (AppTest) 10 dari 10 lulus.
  • Lima pertanyaan inti terhadap view KPI: 3 dari 5 sama persis (pengganti tidak mendukung pengelompokan mingguan dan RTY per model).
  • Sidik jari data simulasi cocok dengan DataCenter (6 dari 6 berkas).

Batasan

  • Data simulasi; Claude tidak dipanggil. Akurasi, latency (3 detik), harga token, menit manual, dan volume adalah asumsi atau hasil pengganti.
  • Golden set 30 pertanyaan ditulis orang yang sama dengan pengganti dan guardrail; hasil optimistis.
  • Aplikasi belum di-deploy; target "orang awam dalam 1 menit" belum diuji.
